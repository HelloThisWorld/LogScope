# v0.3 case baseline — 5M records, 1,000 evidence

Measured 2026-08-05 with `bench_case` (release build) over the
deterministic ChaCha8 corpus (ADR-0010, seed 20260729). Every number
below is a real measurement from one run on the reference machine; no
figure is estimated or interpolated.

Reproduction:

```powershell
cargo run --release -p logscope-testsupport --bin bench_case -- 5000000 --evidence 1000 --fresh
```

Machine: i9-12900KF (24 threads), 64 GB RAM, NVMe, Windows 11 Pro.
Corpus: 5,000,000 JSONL records, 1,205 MiB.

## Results

| Operation | Measured | Notes |
|---|---|---|
| Import + index build (5M) | 222,876 ms | 22,434 rec/s through the real pipeline |
| Pin 1,000 events | 103,500 ms | **103.5 ms/pin** — each pin resolves the record against the 5M canonical store and captures a bounded snapshot |
| Pin one 500-id selection | 1,757 ms | multi-row capture in one service call |
| Verify 1,001 evidence | **1,097 ms** | `dataset_lookups = 1` — asserted in the bench binary; the batched resolver issues **one** canonical id-set lookup for the whole run (~1.1 ms/evidence) |
| Verify cancellation latency | p50 684 ms, max 745 ms | cancel → return, measured mid-run over 5 repetitions |
| Timeline (1,001 entries) | 4 ms | full merge + envelope decode |
| Report, Markdown, all 1,001 evidence | 62 ms | 666,904 deterministic bytes |
| Bundle export | 2,875 ms | includes the referenced-record parquet subset joined against the 5M store |
| Peak working set | 1,734 MiB | whole benchmark process, import included |

## Reading the numbers honestly

- **The no-N+1 property holds at scale.** 1,001 evidence items verified
  with exactly one dataset lookup — the bench binary *asserts*
  `dataset_lookups == 1` and would panic on regression, so this row is a
  test as much as a measurement.
- **Per-pin latency (~104 ms at 5M) is an interactive number, not a
  batch number.** A user pinning one event waits ~0.1 s. Pinning
  thousands sequentially is not a supported workflow; if a bulk-pin API
  is ever wanted, it needs its own batched design.
- **Cancellation latency is bounded by the current phase, not by the
  checkpoint.** Cancelling mid-verify returns in ~0.7 s because the
  in-flight batched engine query completes before the next
  cancellation checkpoint observes the flag. The engine-level interrupt
  is not wired into verify's internal queries today; if sub-100 ms
  cancel latency is ever required for verification, that is the change
  to make. Recorded as-is — the number is the truth of the current
  build.
- **An accidental honesty proof:** the 1,000 event pins verify as
  `source_missing`, not `verified` — the bench corpus lives in a temp
  directory that is deleted after import, so the resolver correctly
  reports "canonical data resolves, original source file is gone"
  instead of pretending full verification. The one `verified` item is
  the selection pin, whose reference checks canonical identity only.
