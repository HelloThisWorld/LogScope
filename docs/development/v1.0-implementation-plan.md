### B-4 — packaged executables were built in development mode

Found by running the shipped 0.2.1 archive: the window opens and displays the
WebView2 error page `localhost refused to connect` (`ERR_CONNECTION_REFUSED`)
instead of LogScope.

`scripts/package-portable.ps1` built the shell with
`cargo build --release -p logscope-desktop`. A plain cargo build does not embed
`frontendDist`; the binary loads the UI from `devUrl`
(`http://localhost:5173`). Building through the Tauri CLI embeds the frontend.
Verified by comparing both binaries for the built asset names
(`assets/index-*.js`, `assets/index-*.css`): absent from the cargo build,
present from the CLI build.

**Every portable artifact ever produced was affected** — 0.0.0, 0.2.0 and
0.2.1 all fail the same check. The defect is invisible at packaging time
because the build succeeds and the application does start, which is how it
survived from v0.0.

This also invalidates one piece of inherited evidence: the v0.10 record's
claim that "the packaged 0.2.0 `logscope.exe` smoke-launched in the v0.9
session". It launched; it did not render. Any future launch smoke test must
assert on rendered content, not on process start.

Fixed by building through the Tauri CLI and by making packaging **fail
closed**: the script now parses the asset references out of the built
`index.html` and asserts each is present inside the executable. The guard was
verified to reject the previously shipped 0.2.0 binary and accept the
corrected one.

### B-1 — cancellation dropped at query start (was "F-1")

The v0.10 record classified the intermittent
`external_cancellation_maps_to_cancelled` failure as a
*test-reliability defect*, with memory pressure from concurrent
cross-join tests as the leading hypothesis, and deliberately left it
undiagnosed. **That diagnosis was wrong, and the defect is larger than
recorded.**

Root cause, established by direct probe rather than inference:
**DuckDB clears any pending interrupt when a query begins.** An
interrupt raised between the cancel request and the engine entering
execution is silently discarded, and the query then runs to completion.

Decisive evidence — probe that cancels *before* running the cross join:

```
PROBE pre-query-interrupt:  elapsed=18.4721975s result=Ok(90000000000)
PROBE uninterrupted:        elapsed=19.1856998s result=Ok(90000000000)
```

The cancelled query ran to completion and returned a value. The v0.10
record's observed 20.37 s failure matches the query's **natural
completion time**, not an out-of-memory path — the failing assertion
printed a successful result, not an engine error.

**This is a production defect, not a test artifact.** Both production
call sites cancel exactly once from a polling thread and then return:

- `crates/logscope-app/src/explorer.rs:195` — `compute_field_stats`,
  budget **600 s**;
- `crates/logscope-app/src/export.rs:328` — export streamer, budget
  **24 hours**.

A cancel landing in the pre-execution window is therefore never
retried, and the user's cancellation is silently ignored for the whole
budget.

Fix (`crates/logscope-query/src/cancel.rs`): `run_bounded` now
short-circuits to `Cancelled` when cancellation was already requested
before the query starts, and the watchdog **re-asserts the interrupt on
every 25 ms poll while cancellation is pending**, so a dropped
interrupt is re-delivered once the query is actually executing. A query
that finishes before the interrupt lands still returns its value:
cancellation remains best-effort and finished work is not discarded.

Regression test `cancellation_before_query_start_is_not_lost`
(`crates/logscope-query/tests/analysis_proofs.rs`) was **verified to
fail without the fix**, with exactly the observed
`Ok(90000000000)` after 20.74 s, and to pass with it. The pre-existing
assertion in `external_cancellation_maps_to_cancelled` was **not
relaxed** and is unchanged.

One candidate regression test was written and then **removed**: a
"cancel racing query start" test passed both with and without the fix
on this machine, so it proved nothing and carried the same timing
dependence that produced F-1. The watchdog re-assertion path cannot be
forced deterministically through the public API; it is covered by
reasoning about the two production call sites above, not by a test that
would only appear to cover it.

## Preflight decision (per milestone rules)

The v1.0 prompt's stop rule is explicit: *"If a major baseline
capability never existed and adding it would be a new product feature
or incompatible redesign, stop before versioning the repository as
1.0.0."* and *"If a candidate behavior is ambiguous, contradictory,
untested, or unsafe, do not freeze it."*

Every v1.0 work package is a *freeze* package that presupposes the
thing it freezes:

| WP | v1.0 asks us to freeze | Prerequisite state |
|---|---|---|
| WP1 | GA baseline, blocker closure, public contract census | RC does not exist; census done, result is this document |
| WP2 | contract catalogue, version policy, schema publication | 5 of 14 versioned surfaces are final; no schema tree |
| WP3 | workspace, source, ingestion, migration contracts | one migration edge (v2→v3); no ledger, spool, rotation |
| WP4 | canonical log, metric, span, provenance models | metrics and spans unbuilt |
| WP5 | query language + shared query semantics | **closest to ready** — but no CLI/Agent/dashboard to prove equivalence against (gate 75) |
| WP6 | analysis, evidence, report, bundle, dashboard | analysis, reports, bundles, dashboards unbuilt |
| WP7 | Agent Query Protocol v1 graduation | nothing to graduate |
| WP8 | extension manifest v1 | nothing to graduate |
| WP9 | complete offline documentation | would document unbuilt behavior |
| WP10 | deterministic samples and tutorials | no import/analysis/evidence chain to demonstrate |
| WP11 | payload, checksums, SBOM, signing boundary | no payload manifest, no SBOM tooling |
| WP12 | disconnected Windows install/upgrade/removal matrix | no v0.10 payload to upgrade from |
| WP13 | conformance, compatibility, drift, cross-platform CI | no schemas to check drift against |
| WP14 | Scenarios A–F | every scenario depends on the above |
| WP15 | version freeze at 1.0.0 | would make 0.2.0-level code claim GA |

The specific irreversible harms avoided by not proceeding:

1. **A frozen public contract catalogue is the one artifact that cannot
   be corrected later.** Its entire purpose (gate 3 of the milestone
   goal) is to let a future 1.x release decide whether a change is
   additive, deprecated or breaking. A catalogue that omits metrics,
   spans, sessions, rotation lineage, the Agent registry and the
   extension manifest would classify most 1.1 work as "additive" when
   it is in fact the first definition of the contract — permanently
   destroying the signal the catalogue exists to carry.
2. **Declaring `LANGUAGE_VERSION 1` stable now** would freeze a grammar
   with no metric, trace, correlation or analysis selectors, and v0.6
   and v0.8 would then have to either break stable v1 or bolt their
   semantics on as a parallel dialect.
3. **Graduating the Agent protocol to `v1`** is impossible: there is no
   `v1alpha1` to graduate. Inventing operations to fill a stable `v1`
   registry is precisely the "No new Agent operation may be added
   merely to make v1 look richer" boundary.
4. **Publishing an SBOM and release manifest for a 0.2.0 portable ZIP
   labelled 1.0.0** would mean the first immutable GA artifact set
   describes a product that cannot perform either advertised public
   workflow.
5. **Setting version 1.0.0** is forbidden by the prompt's own rule: "Do
   not set version 1.0.0 early to make incomplete work appear
   complete."

Per the prompt's blocker procedure, the repository is left valid, the
blockers and their remediation path are documented here, only coherent
verified work is committed, and a ready-to-run continuation prompt is
provided below.
