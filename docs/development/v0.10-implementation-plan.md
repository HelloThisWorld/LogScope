### Finding F-1 — intermittent failure in `external_cancellation_maps_to_cancelled`

Observed once this session, on the **first** `cargo test --workspace`
run: `crates/logscope-query/tests/analysis_proofs.rs:423` panicked;
the `analysis_proofs` binary reported `4 passed; 1 failed` and took
**20.37 s**. On the second full-suite run the same binary was green in
**0.23 s** (200/0 overall). Targeted reruns did **not** reproduce it:
5/5 green in isolation, 6/6 green under six concurrent copies.

Diagnosis is **not** yet established and is deliberately not guessed.
What is known:

- `run_bounded` (`crates/logscope-query/src/cancel.rs:70-78`) checks
  `handle.was_cancelled()` **before** `timed_out`, so a lost DuckDB
  interrupt alone cannot mis-map a cancelled run to `Timeout`.
- The assertion therefore failed on a value that is neither
  `Cancelled` nor produced by the timeout path — most consistent with
  a **non-interrupt engine error** (the two tests in that binary each
  run a `range(300000) × range(300000)` cross join concurrently, so
  memory pressure is the leading hypothesis), which would fall through
  to `Err(QueryError::Engine(e))`.
- The 20.37 s vs 0.23 s wall-time gap supports "engine gave up under
  pressure" over "interrupt was lost then timed out at 60 s".

**Not repaired in this session, by design.** The hypothesis is
unconfirmed, and patching production cancellation mapping or relaxing
the assertion on an unreproduced failure would be exactly the guessing
the milestone rules forbid. Classified as a **test-reliability defect,
release-blocker class for any RC**: a flaky cancellation proof
silently undermines every gate that depends on it (v0.10 gates 19, 89,
98, 104). Remediation path recorded below.

## Preflight decision (per milestone rules)

The v0.10 prompt's stop rule is explicit: *"If a required baseline
feature never existed and implementing it would require a new
incompatible architecture or product capability, stop before freezing
the wrong behavior."* and *"Do not silently reimplement v0.0 through
v0.9 or replace working canonical, query, analysis, evidence, report,
dashboard, Agent, profile, receiver or package contracts."*

Every one of v0.10's sixteen work packages is a *hardening* package
that presupposes the thing it hardens:

| WP | v0.10 asks us to harden | Prerequisite state |
|---|---|---|
| WP1 | durable-state catalogue + fault harness over spool, ledger, active segments, registry, backups, crash records | **absent** (v0.7/v0.9); only immutable segments + SQLite exist |
| WP2 | consistent workspace backup and non-destructive restore | **no backup format exists**; nothing to snapshot beyond a v0.2-level workspace |
| WP3 | atomic migrations across "every advertised source version" | **one real edge (v2→v3)**; v0.4–v0.9 schemas do not exist |
| WP4 | interrupted import/spool/active-segment/publication recovery | staged-import recovery exists and is green; **spool, frames, checkpoints, active segments do not** |
| WP5 | ledger repair, safe rescan, index rebuild, dataset integrity | **no ledger, no rebuildable index inventory, no integrity scanner** |
| WP6 | safe mode, crash records, redacted diagnostics | **none exist**; redaction itself is unbuilt v0.3 W6 |
| WP7 | 10M + multi-signal benchmark contract | log generators exist; **metric/span/session pipelines to measure do not** |
| WP8 | query/UI perf, bounded caches, plan diagnostics | query layer exists and is measured; **cache registry and typed-plan diagnostics do not** |
| WP9 | runtime/export/archive/local-interface security | regex + FTS + offline probes green; **no archive path, no HTML/MD/CSV renderers, no auth** |
| WP10 | dependency inventory, licenses, SBOM, threat model | **none exist** beyond a 41-line notices file |
| WP11 | first run, accessibility, partial states, storage, retention | **no first-run flow, no packaged examples, no retention UX** |
| WP12 | canonical payload, release manifest, checksums, reproducibility | **no payload manifest, no release manifest, no build record** |
| WP13 | graphical extractor, ZIP, staged replacement, removal | **no extractor** — one artifact path only |
| WP14 | optional signing, update manifest, release CI | **no signing stage, no update manifest, no release CI** |
| WP15 | docs, upgrade guide, release notes, 0.10.0 versioning | would document unbuilt behavior; version is 0.2.0 |
| WP16 | full validation + Scenarios A–E | every scenario depends on the above |

Implementing v0.10 now would require inventing v0.4–v0.9 first — a
new product capability per milestone — and then hardening the
invention. That is precisely the "new incompatible architecture"
the stop rule names. The specific irreversible harms avoided:

1. **A backup manifest frozen against a v0.2 workspace** would omit
   metrics, spans, spool, ledger, checkpoints, registry snapshots and
   compiled-plan caches — every authoritative store v0.6–v0.9 adds.
   v0.10's own honesty contract says a backup is "complete" only when
   its manifest truthfully describes every included and excluded
   authoritative dependency. A manifest written today would be
   **structurally incapable of being truthful** later, and backup
   formats are the one artifact you cannot retroactively fix: old
   backups outlive the code that wrote them.
2. **A migration graph and downgrade guard frozen now** would claim
   coverage of "every advertised source version" while knowing only
   v2→v3, and would assign migration numbers that the completed
   v0.4–v0.9 chain must then collide with or skip.
3. **Payload/release manifests and an SBOM frozen now** would describe
   a single-artifact 0.2.0 portable ZIP and be presented as the RC
   distribution contract, while the dual-artifact byte-equivalence
   requirement that gives the contract its meaning stays untestable.
4. **RC budgets published now** would be measured on log-only
   workloads and then inherited by v0.6–v0.8 signal pipelines that
   were never in the measurement — the "faster wrong result is FAIL"
   rule inverted into "budget met because the work didn't exist yet".

Per the prompt's blocker procedure, the repository is left valid, the
blocker and its remediation path are documented here, only coherent
verified work is committed (this record), and a ready-to-run
continuation prompt is provided below.
