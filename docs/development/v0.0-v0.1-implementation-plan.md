## Decisions already made (to be recorded as ADRs)

1. **Module boundaries**: ten crates as above; desktop shell thin; services
   shared by UI/CLI (ADR-0001).
2. **Offline packaging**: bundled DuckDB with static `json`+`parquet`;
   `autoinstall_known_extensions=false` + `autoload_known_extensions=false`
   on every connection; `httpfs` absent; bundled SQLite (ADR-0002).
3. **Workspace**: SQLite (`workspace.db`) owns metadata; Parquet owns bulk
   records; forward-only transactional migrations; manifest.json versioned
   (ADR-0003).
4. **Canonical model**: OTLP-superset records; typed `AnyValue` with tagged
   canonical JSON; BLAKE3 content IDs (`res-`/`scp-`/`log-`/`met-`/`spn-`);
   hashes exclude wall-clock + workspace-instance fields; golden pin test
   guards encoding changes (ADR-0004).
5. **Import atomicity**: stage -> rename into `data/` -> single SQLite tx;
   recovery discards staging, removes orphan files, fails interrupted jobs,
   deletes empty staging datasets (ADR-0005).
6. **Query/FTS**: DuckDB `read_parquet` over immutable published segments
   only; full-text via SQLite FTS5 (`indexes/fts-logs.db`) because DuckDB
   fts is not statically available and INSTALL would require network —
   verified by executable probe (ADR-0006).
7. **Cancellation**: cooperative `JobControl::checkpoint()` between batches;
   DuckDB `interrupt_handle` for queries (probe test proves usability after
   interrupt) (part of ADR-0005/0006).
